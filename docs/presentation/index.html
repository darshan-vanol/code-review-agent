01 · Problem Statement

Two problems, once you have an LLM agent in production

Evaluation

Is the agent actually good?

How do you tell — repeatably, offline, without a human re-reading every diff — whether the agent catches the bugs it should? And can that check gate every PR in CI?

Observability

What happened inside the run?

A review is several LLM calls chained together. Which step said what, using which model, at what token cost and latency — and how do you see that without re-running it by hand?

02 · Problem Statement — The RAGAS Detour

We started with RAGAS. The numbers didn't add up.

RAGAS is the standard framework for evaluating LLM outputs, so it was the natural first choice. Scored with a strong judge model (llama-3.3-70b-versatile) against a 0.75 gate:

faithfulness0.270
answer_correctness0.400

Yet manual inspection confirmed the agent's findings were correct — SQL injection, hardcoded secret, null-deref, and SSRF were all detected and matched the goldens.

03 · Root Cause

RAGAS measures a RAG task. Code review isn't one.

faithfulness

Checks entailment from retrieved context. A review is analytical inference, not extraction — a test-coverage suggestion like "missing test for X" is provably absent from the diff text itself, so a strict NLI judge marks it unsupported every time.

answer_correctness

Assumes one canonical reference answer. The agent correctly returns 3-4 findings per case; each extra correct finding counts as a false positive against a single-finding reference, so the F1-based score collapses.

"A perfect reviewer cannot clear the gate. The eval measures the wrong thing."
— project design notes, on why RAGAS was replaced as the gate
04 · Solution — Evaluation Harness

A detection-based scorer, matched to the actual task

  • Deterministic match per golden finding: same file, overlapping line range, same category.
  • Hybrid LLM "rescue" for anything left unmatched — fail-safe: a flaky judge can only rescue a miss, never downgrade a deterministic match.
  • Gates CI on the aggregate score; recall reported alongside but not gated.
recall = matched_goldens / total_goldens score = clamp(recall − 0.2 × false_positive_rate, 0, 1)

05 · Solution — Langfuse Observability

One trace per review. One span per step.

  • Every review emits one Langfuse trace with a child span per LangGraph node.
  • LLM nodes are generation observations carrying model name + input/output token counts — Langfuse auto-computes cost and latency.
  • Deterministic nodes (ingest, aggregate) are plain span observations.

Three-tier tracer

NoOpTracer → RecordingTracer → LangfuseTracer

Per-node spans are always returned inline in the API response, even with Langfuse disabled. Langfuse is purely additive — never a dependency for basic visibility.

06 · Key Features

What ships beyond the two headline pieces

Golden dataset + CI gate

20 hand-authored cases; the eval job comments the score table directly on the PR and fails the build below threshold.

Resilient LLM nodes

Each node retries once on malformed output, then degrades to an empty finding list — a bad model response never crashes a review.

Provider-agnostic adapters

One LLMProvider protocol behind mock / groq / gemini — swap providers with one env var.

Live dashboard

Review Playground (paste a diff or PR URL) and Eval Analytics (score trends) in one Vite + React app.

Offline-first dev loop

The default mock provider runs the whole pipeline with zero API keys — trivial diffs even skip the LLM nodes entirely.

Streaming reviews

/review/stream yields per-node progress as newline-delimited JSON for live UI updates.

09 · Takeaways / What's Next

Match the eval to the task — and keep the trail

  • RAGAS code was kept, not deleted — a documented, reversible decision (evals/ragas_scorer.py remains as an optional, non-gating alternative).
  • Observability should be additive: the system never depends on Langfuse being enabled to be debuggable.
  • A CI gate is only as good as the metric behind it — a failing gate should make you question the metric, not just the agent.

Next up
